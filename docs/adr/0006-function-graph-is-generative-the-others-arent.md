# `function_graph` is a deliberately generative Simulation Type; the physics types still aren't

ADR-0004 fixed Simulation Type to a small, hand-built enum specifically to avoid building a general/generative renderer under an 11-day budget. That held through `spring_mass`/`pendulum`/`projectile`, and we initially extended it the same way for `linear_function` (y = 2x) when a real demo formula came back unsupported. But the next demo formula was a quadratic, and the one after that would have been something else — a fixed enum of "every function shape a classroom might draw" doesn't converge; it just keeps growing one hand-written widget at a time.

We split the concept in two instead of keeping one fixed enum:

- **Physics types** (`spring_mass`, `pendulum`, `projectile`) stay exactly as ADR-0004 describes: real time-evolving simulations, each with its own hand-written RK4 integrator. These aren't static graphs — there's no way to make them generic without actually building a physics engine, which ADR-0004 already rejected.
- **`function_graph`** replaces `linear_function` as a single generic type covering any single-variable `y = f(x)` (linear, quadratic, cubic, trigonometric, exponential, logarithmic, ...). The AI returns an `expression` field (a plain-text algebraic expression in `x` and its chosen parameter keys, always solved explicitly for `y` even if the handwritten formula was implicit, e.g. "2y = 3x" -> `"m*x + b"`) alongside the usual `parameters`, and the frontend evaluates it via `mathjs` (`view/src/lib/functionGraph.js`) rather than a hand-written-per-formula renderer.

This is a real, hard-to-reverse trade-off, not a free upgrade: we are now trusting the AI's `expression` output to be both syntactically valid and semantically correct, parsed by a real expression engine instead of fixed, predictable code paths. We mitigate the "syntactically invalid" case (a malformed expression can't execute as code either way, since `mathjs.compile` only ever produces a sandboxed evaluator, never raw `eval`/`new Function`) by rendering a "couldn't render this function" fallback instead of crashing — see `FunctionGraphWidget`'s `compileExpression` guard. We do not mitigate the "semantically wrong but valid" case (e.g. the AI returns a plausible-looking but incorrect expression for the drawn formula); that risk is accepted as inherent to any Simulation Type that's bound to free-form AI output rather than classification into a closed set.

**Rendering engine, revised:** `function-plot` (a d3-based library purpose-built for graphing math functions) was tried first for the actual curve/axis rendering, keeping evaluation on our own sandboxed `mathjs` path via its `fn` callback option. It was dropped after failing silently in production in ways that couldn't be fully diagnosed without real-browser access -- repro attempts in a standalone Node+jsdom script showed its CJS/ESM module interop behaving inconsistently outside Vite's own bundler, and when it failed in the browser the container had no reserved size, collapsing to an invisible box with no visible error. Rendering now uses a hand-rolled canvas (`lib/axisTicks.js` for "nice" tick values, dynamically sized to the container's actual measured width via `canvas.clientWidth` rather than a fixed pixel constant). This sacrifices `function-plot`'s nicer adaptive-domain/zoom/discontinuity handling for a renderer we can fully verify ourselves end-to-end -- given we had no way to test the third-party library's real-browser behavior in this environment, "fully verifiable" won out over "nicer when it works."

**Parametric curves, added:** a circle (`x^2 + y^2 = r^2`) fails the vertical-line test, so it can never be expressed as a single `expression` -- that representation can only ever draw a semicircle. Rather than add a dedicated `circle` Simulation Type (which would just restart ADR-0004's "one hand-written widget per formula shape" growth problem one level down), `function_graph` now accepts a second, mutually-exclusive representation: `parametric_x`/`parametric_y`, two mathjs expressions in a parameter `t` (conventionally `[0, 2*pi]`) that trace the full curve (a circle of radius `r` becomes `parametric_x: "r*cos(t)"`, `parametric_y: "r*sin(t)"`). The AI picks whichever representation applies per the prompt's vertical-line-test instruction; the frontend samples whichever fields are present (`lib/functionGraph.js`'s `sampleParametric`) and closes the drawn path when parametric. Pan/zoom (`lib/graphViewport.js`) was added at the same time, operating on a **Graph Viewport** independent of both representations.
