# `function_graph` is a deliberately generative Simulation Type; the physics types still aren't

ADR-0004 fixed Simulation Type to a small, hand-built enum specifically to avoid building a general/generative renderer under an 11-day budget. That held through `spring_mass`/`pendulum`/`projectile`, and we initially extended it the same way for `linear_function` (y = 2x) when a real demo formula came back unsupported. But the next demo formula was a quadratic, and the one after that would have been something else — a fixed enum of "every function shape a classroom might draw" doesn't converge; it just keeps growing one hand-written widget at a time.

We split the concept in two instead of keeping one fixed enum:

- **Physics types** (`spring_mass`, `pendulum`, `projectile`) stay exactly as ADR-0004 describes: real time-evolving simulations, each with its own hand-written RK4 integrator. These aren't static graphs — there's no way to make them generic without actually building a physics engine, which ADR-0004 already rejected.
- **`function_graph`** replaces `linear_function` as a single generic type covering any single-variable `y = f(x)` (linear, quadratic, cubic, trigonometric, exponential, logarithmic, ...). The AI returns an `expression` field (a plain-text algebraic expression in `x` and its chosen parameter keys) alongside the usual `parameters`, and the frontend evaluates it via `mathjs` (`view/src/lib/functionGraph.js`) rather than a hand-written-per-formula renderer. Rendering itself uses `function-plot` (a d3-based library purpose-built for graphing math functions: adaptive axis ticks, grid, correct handling of discontinuities) rather than hand-rolled canvas axis/curve-drawing code -- `function-plot`'s `fn` option accepts a plain JS callback, so it only ever calls back into our own sandboxed `mathjs` evaluator, never its own string parser, keeping evaluation on a single, already-tested path.

This is a real, hard-to-reverse trade-off, not a free upgrade: we are now trusting the AI's `expression` output to be both syntactically valid and semantically correct, parsed by a real expression engine instead of fixed, predictable code paths. We mitigate the "syntactically invalid" case (a malformed expression can't execute as code either way, since `mathjs.compile` only ever produces a sandboxed evaluator, never raw `eval`/`new Function`) by rendering a "couldn't render this function" fallback instead of crashing — see `FunctionGraphWidget`'s `compileExpression` guard. We do not mitigate the "semantically wrong but valid" case (e.g. the AI returns a plausible-looking but incorrect expression for the drawn formula); that risk is accepted as inherent to any Simulation Type that's bound to free-form AI output rather than classification into a closed set.
