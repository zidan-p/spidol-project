# AI Trigger pipeline talks to an OpenAI-compatible endpoint, not the `google-genai` SDK

Ticket 04 originally built the AI Trigger pipeline directly against Google's own `google-genai` SDK (`genai.Client`, `client.models.generate_content(...)`, `response_schema=PydanticModel`), hard-coding Gemini as the only reachable provider.

We replaced this with a provider-agnostic client built on the `openai` Python package, talking to any OpenAI-compatible chat-completions endpoint (`client.chat.completions.create(...)`, structured output via `response_format={"type": "json_schema", ...}`). `server/ai/vision_pipeline.py`'s `make_live_client(api_key, base_url)` defaults `base_url` to Gemini's own OpenAI-compatible endpoint (`https://generativelanguage.googleapis.com/v1beta/openai/`) and `DEFAULT_MODEL` to `gemini-3.1-flash-lite`, so the out-of-the-box behavior is unchanged. `main.py` exposes `AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL` env vars and `--ai-base-url`/`--ai-model` CLI flags to point at a different provider/router instead — e.g. OpenRouter (`https://openrouter.ai/api/v1`) — without touching `vision_pipeline.py` itself.

Trade-off: we lose `google-genai`'s typed convenience wrapper (e.g. passing a Pydantic model directly as `response_schema`) in exchange for provider flexibility — useful given how fast the Gemini model lineup has already churned once in this project's own history (see `vision_pipeline.py`'s model-name note), and given the team's interest in routing through OpenRouter for redundancy/pricing reasons. The module was renamed `gemini_pipeline.py` -> `vision_pipeline.py` to match: it was never really Gemini-specific logic, just a Gemini-specific client.
